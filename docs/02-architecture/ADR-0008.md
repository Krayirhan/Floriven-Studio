# ADR-0008 — Semantic UX plan and presentation strategy boundaries

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-08-09 |
| Owner | Architecture + AI Lead |
| Required reviewers | Tech Lead, Frontend Lead, Security Owner |

## Context

ADR-0006 separates product domain from visual style, and ADR-0007 makes the
`ProductBlueprint` the source of screen information architecture. The current
generation output still combines task structure, component choice, and visual
treatment in one screen tree. That leaves no enforceable boundary preventing a
style selection from changing an interaction pattern or a generic Card stack
from becoming the fallback for unrelated screen jobs.

The V2 roadmap requires a staged pipeline while preserving the canonical
DesignSpec contract and the existing generation job, idempotency, and tenant
boundaries.

## Decision drivers

- Preserve a stable, versioned canonical DesignSpec.
- Keep style from deciding navigation, screen archetype, actions, or content hierarchy.
- Allow deterministic structural and semantic validation before render.
- Support localized patch repair without replacing unrelated screens.
- Avoid provider-specific models or response formats in domain code.
- Introduce the migration incrementally without breaking v1 clients.

## Alternatives

### A — Continue composing a final DesignSpec in one generation step

This has the smallest short-term implementation cost but cannot make UX versus
presentation ownership enforceable. It preserves the current failure mode:
structurally valid output may still use the wrong pattern, action placement, or
surface hierarchy.

### B — Introduce semantic planning stages and compile to DesignSpec

Introduce `UXSpec`, `PatternPlan`, and `PresentationSpec` as internal,
versioned stage contracts. `UXSpec` owns archetype, information hierarchy,
navigation mode, action intent, and content density. `PresentationSpec` owns
tokens, typography treatment, color, radius, and surface treatment. A semantic
composer combines these contracts into the existing DesignSpec only after the
UX contract is frozen and passes static validation.

This raises initial implementation and test cost but keeps the DesignSpec v1
output and its consumers compatible.

### C — Create a separate renderer-owned layout document

This isolates rendering concerns, but duplicates canonical model ownership and
would require a new synchronization protocol for editor, snapshot, and export.

## Proposed decision

Choose alternative B, subject to the required approvals above.

The planned internal sequence is:

```text
ProductBlueprint → ScreenGraph → UXSpec → PatternPlan → SemanticDesignSpec
→ Static lint → PresentationSpec → DesignSpec → render/geometry validation
```

The following rules apply:

1. `StylePreset` and `PresentationSpec` must not change UXSpec fields.
2. LLM stages express semantic intent and token references, not raw pixel coordinates or safe-area offsets.
3. Each new stage validates its schema and references before reaching the next stage; only the canonical DesignSpec reaches the editor or persistence path.
4. `DesignSpecPatch` remains identity-based; repair stages may modify only addressed nodes and must re-run the same validators.
5. The existing DesignSpec v1 and generation API remain backward compatible throughout the migration.

Implementation is authorized with feature-gated, backward-compatible internal contracts.

## Consequences

Positive:

- Separates product UX decisions from art direction.
- Makes Pattern Registry, structural linting, and visual repair measurable follow-on stages rather than prompt conventions.
- Lets v1 consumers remain on their existing canonical contract.

Negative:

- Adds stage schemas, validation, telemetry, and test fixtures.
- Increases generation orchestration complexity and potential latency.
- Requires explicit model capability routing for each stage.

Rollback:

- New stages are internal and feature-gated. A failed rollout can route to the current ProductBlueprint-to-DesignSpec path without migrating stored v1 DesignSpecs.

## Validation before acceptance

- Produce an implementation spike for one finance flow with both auto and template styles.
- Confirm identical UXSpec hashes across style variants for the same brief.
- Confirm a semantic patch preserves unrelated node IDs and screens.
- Run tenant isolation, schema, and benchmark regression tests.
- Review the stage payloads for prompt-injection boundaries and absence of sensitive prompt/design content in logs.
